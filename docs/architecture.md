# 架构与协议

## 边界

`server/engine.js`：纯规则和房间状态机；只读 `publicView` / `privateView` 用白名单构造返回值。身份仅存服务端。逆仆角色和当前阵营分开存储；转阵营不修改已完成任务。角色逻辑在领域层，不在按钮事件中判胜负。
`server/store.js`：SQLite房间、会话哈希、幂等回执。事务回滚不留部分提交。
`server/app.js`：输入校验、认证、限流、事务执行；不接受请求体中的用户ID或房主标记。单进程，无 WebSocket，手机每2.5秒拉取专属公共视图。
`miniprogram`：一个完整牌桌页面，覆盖入口、房间与各阶段；独立的私密面板，每个阶段默认遮盖。

## 请求

| 方法/路径                      | 用途                               |
| ------------------------------ | ---------------------------------- |
| GET /health                    | 存活检查                           |
| GET /api/boards                | 板子清单、可用状态与板子详情      |
| POST /api/login                | 微信 code 换本应用会话             |
| POST /api/dev-login            | 显式 DEV_AUTH 开启时的匿名联调登录 |
| POST /api/rooms                | 创建；name、board、capacity        |
| POST /api/rooms/:code/join     | 加入或恢复成员；name               |
| GET /api/rooms/:code           | 仅本人有权看的公共状态             |
| GET /api/rooms/:code/private   | 本人身份、视野及合法行动           |
| POST /api/rooms/:code/commands | 带stage的命令                      |

除登录/健康/板子外请求头 `Authorization: Bearer <token>`；所有房间写请求还需要 `Idempotency-Key`（16–100位字母数字、连字符、下划线）。请求上限8KB。返回错误 `{error: 中文原因}`，400非法输入/动作，401会话无效，403权限不足，404不存在，409过期阶段/冲突/未完成，429限流，5xx服务异常。

命令 `type`：seat(seat)、ready(ready布尔)、configure(board,capacity)、start、propose(team座位数组)、submit(value)、advance、terminate、rematch、transfer(seat)、leave；影中执刃辅助模式另有 offline（转线下）和 closeOffline（线下完成，仅结束不判胜）。全部带最新公共视图的stage。隐藏角色的合法动作从私密视图获取，服务端再次校验。

每次阶段转换随机生成stage，阻止前一阶段动作重放。未收齐的秘密提交不改stage，也不发公共版本变更；按需模式最后一份提交会触发结算并更新stage。前台请求尚未确认则保留完全相同的请求体和编号重试；回执只存确认信息，不存角色/旧私密视图。幂等回执验证用户+编号+路径及请求体指纹。

## 管理权限

房主可选板/人数（服务接口）、全员准备后开局、请求推进、终止、结束后重开、准备阶段转交房主。不能代选他人的秘密行动、查看他人秘密或更改已提交行动。按需模式可确认后结束等待，未提交按公开阶段规则处理，见下方“自动结算与房主截止”。新成员无法加入进行中的房间。离开只允许准备阶段；房主有其他成员时必须先转交。房主可在准备阶段、已结束或已终止后移出其他玩家；进行中不可移出。无机器人补票或断线自动胜负。

## 数据保留与运行限制

当前MVP不自动清理房间/回执；长期开服需按实际保留策略增加清理，不能删除进行中对局。每分钟有IP/用户/登录/建房限流；反向代理下按连接IP限流，不信任任意客户端X-Forwarded-For。一个代理IP代表全部用户时需按部署规模调整或在可信代理限流。

持久化完成才返回确认；失败事务回滚。SQLite同步事务用于低并发线下房间，适合第一版；没有假装支持无限并发或多节点实时同步。

未确认的建房/加入请求只缓存不含秘密的请求数据与编号，应用重启可以重放；身份、私密视野和秘密动作不持久化到小程序存储。

## 成员房间恢复

`GET /api/me/rooms` 返回当前用户可见的个人牌桌记录，包括房间码、板子、公共状态、公开人数、房主昵称、本人座位与关系、个人备注、最近进入及房间活动时间。没有全局房间目录，不返回秘密角色、动作、成员列表或秘密提交计数。新邀请优先显示邀请入口；切换界面保留成员关系，真正离开仍走受规则约束的 leave 命令。

SQLite `room_entries` 以 `(uid, code)` 隔离个人快照、隐藏状态、备注和最近进入时间。现有成员关系在读取时自动补齐；房间写入刷新公开快照，但不改变隐藏状态或访问排序。房间已删除、成员已离开或被移出时只返回该用户此前保存的失效快照，不再提供实时信息；创建时间用于区分重复使用的房间码。

`POST /api/me/rooms/:code` 接受 `hide`、`restore`、`note`、`visit`，要求认证和幂等键；事务内更新个人记录并保存回执，不修改游戏状态。`visit` 额外验证当前成员关系或房主权限。创建、加入与显式进入会恢复条目并更新访问时间，轮询不会恢复隐藏条目。解散仍使用原来的房主权限、阶段校验和幂等删除接口。

## 管理与正式陪测（2026-09-16）

`server/admin` 提供独立 `/admin` 页面和 `/api/admin/*` 接口。仅配置 ADMIN_ORIGIN 与 ADMIN_KEY 后启用；正式环境要求 HTTPS。管理接口使用源地址检查与独立 HttpOnly Cookie 会话，不接受普通玩家 Bearer token 作为管理员凭据。当前单管理密钥模式，会话8小时有效，重启/退出失效。

管理概览使用字段白名单，只有房间号、板子、人数、阶段和测试标记，不返回真人角色或行动。管理写操作要求当前 stage、房间号确认和原因，变更与审计在同一 SQLite 事务中完成。可结束、同房重开、删除房间、切换准备阶段房间的陪测标记以及清理测试账号。

现有房间可以在 lobby 开启 testRoom，保留原玩家；公共玩家视图与房间摘要返回该标记。陪测账号 UID 以 test: 开头，绑定房间及管理员会话，访问原玩家接口时同时检查管理会话和测试房间标记。所有游戏操作仍走原引擎和幂等回执。关闭陪测、清理测试座位或管理删除房间会撤销对应陪测会话。管理操作及成功陪测写操作记录在 admin_audit 中，不记录秘密操作值。

本地 /dev 开关和本机访问限制不变。生产不启用 /api/dev-login；正式陪测通过受保护的 /api/admin/actors 获取独立测试账号。

## 自动结算与房主截止（2026-09-18）

当前按需模式的 `submit` 在写入最后一份合法提交时调用统一结算逻辑。提交与结算在同一房间副本和数据库事务内提交，结算后生成新 `stage`；如技能链停在追加行动，则等待该新阶段全员提交。普通中间提交不改变 `stage`。原请求编号重试仍使用幂等回执，旧阶段的新请求被拒绝。历史顺序模式维持原推进方式。

新增房主命令 `closeWaiting`，请求需包含当前 `stage` 与 `confirm: true`。服务端依据公开阶段选择处理规则，不接受客户端指定默认秘密行动：投票缺失值填内部 `abstain`，结果用 `approve: null` 表示弃权、门槛不变；技能缺失值仅在合法选项含 `pass` 时填 `pass`；任务和必选目标操作只作废。所有已提交行动保持不变。截止只作用于请求绑定的阶段，不延伸到新触发的追加行动。

公开视图新增 `operationStatus`（本人的操作提示）及仅房主可用的 `closeWaiting`（阶段处理说明）。策略不依赖秘密角色，不增加普通玩家的他人提交进度权限。截止技能记录只注明本阶段按不使用／确认处理；技能过程仍由既有可见性设置过滤。小程序和网页版从过滤后的公开历史推导最近结果，无需新增缓存或私密持久化。旧版 `settleTool` 接口保留，便于处理升级前已收齐但尚未结算的操作。


## 房主移出玩家（2026-09-18）

房主命令 `kick` 仅在 `lobby`、`ended`、`terminated` 可用，需要 `stage`、`seat`、`targetId` 和 `confirm: true`。每次入座生成新的成员编号；只有房主的公开视图包含 `players[].managementId`，旧房间使用房间码和用户 ID 的 SHA-256 摘要兼容，不向客户端暴露用户 ID。服务端同时核对成员编号与座位，避免离席、换座或同账号重新加入后被过期确认误移出。

移出后刷新阶段编号，保留其他成员的座位、准备状态及已完成对局记录。房间保存被移出账号标记，以便公共视图、私密视图和操作接口统一返回 403 与“你已被房主移出房间”；房间列表自动移除该成员关系。客户端清除私密展示并回到首页。此能力不是封禁：准备阶段允许重新加入，重新入座生成新成员编号并清除移出提示标记。结束后需由房主同房重开再补人。

小程序和网页均在设置页提供选择成员、确认移出和结果反馈。进行中禁用入口并说明原因；未确认的网络请求使用原请求编号和原目标重试，不允许覆盖后再移出另一人。成功刷新名单时保留尚未保存的设置草稿。移出操作写入既有管理审计。

## 个人战绩（2026-09-28）

`GET /api/me/stats` 只读取认证用户的战绩，返回 `total/wins/losses/excluded/winRate`、`byFaction`、按最终阵营和本人角色分组的 `byRole`、按板子与人数分组的 `byBoard`，以及兼容旧客户端的最近 20 局 `recent`。胜率是百分数，保留一位小数；无有效局时为 `null`。该接口不会返回其他玩家的身份、名单或用户 ID。

`GET /api/me/matches?offset=N` 为小程序“对局记录”提供按结束时间倒序的分页明细，每页最多 20 场。只返回认证用户参与的归档对局，包含时间、板子、本人身份与胜负、胜方和同桌成员的座位及当时昵称，不返回其他用户 ID 或身份。未计入战绩的归档对局仍在记录中显示排除原因。

每次发牌生成 UUID `matchId` 和开始时间；进入 `ended` 或 `terminated` 时冻结 `matchRecord`，记录本局参赛者、最终角色和阵营、个人胜负、胜方、来源及排除原因。SQLite `matches` 保存整局信息，`match_players` 以 `(match_id, uid)` 为主键保存个人记录，并以 `(uid, ended)` 建索引。保存房间、归档与请求回执在现有写事务中提交；重复请求或后续保存不会重复计数。冻结记录不随踢人、重开或解散而变化。

`finishTools` 接受 `winner: good | evil | third | null`，只有当前房主可登记，`third` 仅对有盗贼阵营的板子可用。公共 `winnerOptions` 从板子配置生成，不从秘密身份推导。旧客户端缺省胜方仍按未登记处理。自由模式的结束登记和 `closeOffline` 的最终登记标记 `manual`；规则引擎的胜负标记 `system`。陪测房间及含 `dev:` / `test:` 参赛身份的对局正常归档并计入胜率；终止、无胜方及身份不完整的局不计入，旁观者不归档。启动时会补算旧归档中仅因“测试局”被排除且胜方、身份完整的对局，同步个人记录、统计与排行榜；排行榜公开资格不变。

升级不会扫描并回填已经结束的旧房间；升级前已开始、升级后结束的局可在结算时生成归档 ID，未知开始时间为 `null`。现有微信 uid 与游客 uid 不迁移、不合并；此版本没有跨端账号绑定或修改已归档结果的接口。


## 页面导航与个人资料（2026-09-28）

小程序首页是 `pages/lobby/lobby`，与 `pages/me/me` 组成原生底部导航“对局 / 我的”。牌桌保持原邀请路径 `pages/table/table?code=…`，独立展示，不显示 tabBar；返回大厅不执行离席。编辑资料、个人战绩与对局记录分别由 `pages/profile/profile`、`pages/stats/stats`、`pages/matches/matches` 承载。未确认的牌桌操作仅在应用内存保存原请求及幂等键，返回大厅后需先回原桌重试，不持久化秘密行动。网页对应 `#/lobby`、`#/me`、`#/profile`、`#/stats`、`#/table/:code`，支持刷新和浏览器返回。

底栏使用微信原生 tabBar，由框架管理选中态及底部安全区。原自定义组件在每个 tab 页独立创建、默认选中“对局”，再由 `onShow` 修正，会引入选中态及图标跳变；两项固定导航不再维护该组件。页面底部仅保留内容间距，避免重复预留原覆盖式底栏的高度。“我的”页切回时保留已展示的内容并刷新资料与战绩，只将变化的字段传入 `setData`；相同头像及战绩不重新绑定，真实修改仍随刷新更新，迟到响应由请求序号隔离。

认证接口 `GET/POST /api/me/profile` 使用现有 uid。`profiles` 保存昵称、头像哈希、版本和修改时间；POST 要求当前 `version` 与幂等键，同事务保存资料与回执，旧版本返回 409，防止跨设备覆盖。昵称为 1–16 个字符，仅作为新牌桌昵称默认值，不回写房间与历史战绩。微信身份沿用现有登录流程，游客身份不自动合并或绑定。

小程序大厅记录上次读取的个人昵称；再次进入大厅时，如果个人昵称已变化，则清除旧的桌名编辑标记并采用新默认值。仅修改头像、正常刷新或请求期间新输入的桌名不会被覆盖。重叠资料刷新只应用最新响应；已发送或待确认的创建／加入请求仍保留原载荷和幂等编号。

大厅并行读取房间列表与个人昵称，一项失败仍应用另一项的成功结果；自动重连与手动刷新均重新读取昵称，避免连接恢复后输入框仍为空。原生昵称输入框未改变内容的失焦事件不计为手动编辑，实际清空或修改的本桌昵称仍保留。

房间公共接口在原有成员鉴权及字段白名单之后，批量读取当前在座玩家的头像哈希，为 `players[]` 增加 `avatarUrl`（未设置为 `null`）；不返回个人资料昵称、内部 uid 或其他资料字段，也不把头像写入房间与对局快照。头像修改随下一次正常轮询显示，不改变游戏阶段或选人状态；换座时头像跟随玩家。小程序与网页座位卡片保留三列布局和原有点击条件，新增圆形头像、昵称首字占位及独立空位样式。图片失败回退到占位，同一 URL 在当前牌桌内不随轮询重试；离开牌桌重新进入，或头像 URL 从在座玩家中移除后重新出现时允许再次加载。

小程序与网页版仅支持选择内置头像，客户端提交白名单编号；资料接口只接受 `builtin:<id>`、`null`（清除）或省略头像字段（保留），拒绝用户图片数据和外部图片地址，请求体统一限制为 8KB。服务端读取内置图片、校验内容哈希，按 SHA-256 去重保存在 `avatars`；已有上传头像继续读取和展示，改昵称不会清除旧头像。`GET /api/avatars/:hash` 提供带固定图片 MIME 和缓存头的公开图片，以便小程序 image 加载；编辑预览的临时路径不写入数据库。头像不随房间删除。资料接口同时支持 `leaderboardVisible`（布尔值，微信和开发账号默认开启）；旧客户端省略时保留当前设置，微信和开发账号允许开启。排行榜底栏通过 `POST /api/me/leaderboard-visibility` 直接保存该设置，提交 `{leaderboardVisible: boolean}` 与幂等键；在同一事务中读取最新资料并只更新展示设置，不覆盖昵称和头像。资料编辑页不再携带该字段。

## 排行榜（2026-09-28）

小程序 `pages/leaderboard/leaderboard` 和网页 `#/leaderboard` 从“我的”进入，不增加底部导航项。提供 `games`（有效局数）、`overall`（总胜率）、`good`（好人胜率）、`evil`（坏人胜率）四榜，页面只保留周期、指标、榜单与本人战绩，取消规则入口、宣传语及资格说明；底栏左侧突出显示我的名次，右侧仅显示当前指标值（总局数或对应胜率），不重复胜负明细；未上榜时显示“未上榜”。默认全部局数榜；`period=all|month` 切换周期。本月以北京时间及归档结束时间计算，使用月初含、下月初不含的区间，与服务端系统时区无关。

只聚合 `match_players.outcome IN ('win','loss')`，继承归档时的排除规则、最终阵营和个人胜负。手动与系统结果均计入。第三阵营参与总榜，阵营榜只包含对应最终阵营。四榜均有1局有效对局即可参与；阵营榜需在所选周期内有该阵营的有效对局，不设置10局或20局门槛。胜率按原始整数胜负比例比较，避免展示值舍入影响名次；相同比例以局数降序，两项相同则并列跳号（1、2、2、4）。局数榜同局数并列，公开ID仅用于并列玩家稳定分页，不影响名次。

`GET /api/leaderboard?metric=games&period=all&offset=0` 要求普通玩家认证，沿用用户限流与 `Cache-Control: no-store`。参数使用白名单并拒绝重复项；每页20人，最多展示前100位玩家。后续页必须带首屏返回的 `version`，版本变化返回409，客户端自动回到首屏重新加载，避免重复或遗漏。排名在完整合格人群上计算，前100位之外的本人仍返回真实名次。响应字段：

- `metric/period/periodStart/periodEnd/timezone/threshold`：当前统计口径；全部周期的结束边界为 `null`。
- `eligibleCount/maxRows/updatedAt/version/nextOffset/hasMore`：参与人数、展示上限、缓存生成时间及分页状态。
- `rows[]`：独立 `publicId`、当前昵称、头像URL、`rank/isSelf/total/wins/losses/winRate`。不含内部UID、角色、对局明细或房间码。
- `me`：认证用户本人的 `rank/status/remaining/total/wins/losses/winRate`。状态为 `ranked/hidden/unsupported/no_games`，未上榜名次为 `null`，零有效局胜率为 `null`。

`profiles` 迁移新增 `leaderboard_visible`（默认1）和独立随机 `public_id`。微信和开发账号默认公开；尚无公开ID的旧资料在启动时开启展示并生成公开ID，已有公开ID的资料保留其保存的开关设置。公开展示的微信和开发账号参与公共名次；游客和陪测账号仅查看榜单及自己的统计，不支持开启。公开设置文案明确包含全部已归档有效对局，关闭设置不会删除个人战绩。公开ID在后续改名和重启时保持稳定，不返回微信身份派生值；历史昵称和对局快照不用于公开榜单。

`server/leaderboard.js` 按四指标和两周期保留至多8份30秒内存快照，公共聚合缓存与每次按认证用户构造的 `me/isSelf` 分离。新归档或资料变更标记失效，仅在 SQLite 事务提交成功后增加缓存版本；回滚和幂等重放不误刷新，月界与系统时钟回退也触发重算。数据未变化时缓存到期重算保留分页版本，避免阅读时间较长就被迫返回首屏。数据仍来自归档表，无累计计分表或额外服务。部分索引 `match_players_rank_time` 支持有效局时间范围查询，`profiles_public_id` 保证非空公开ID唯一。

部署时先更新并重启后端，自动完成兼容性迁移，再发布小程序。原有资料客户端省略公开设置不会覆盖用户选择；已有战绩直接参与聚合，仍不回填归档功能上线前缺失的对局。启动迁移会创建索引，生产发布前按既有流程备份SQLite数据库。验证包括归档口径、门槛、并列与原始比例、月界、分页版本、榜外本人、隐私、资料版本、幂等、迁移和两端异步响应保护。

### 内置头像

网页版通过同源 `/builtin-avatars.js` 加载同一份目录，静态路由只开放目录列出的头像预览图片。资料编辑页对齐小程序的导航标题、头像下方昵称编辑、风格筛选、四列选择网格及底部固定保存按钮；选中状态由预览路径或已保存的内容哈希识别，选择仅修改草稿，保存继续使用原有版本校验和幂等请求。

小程序内置 108 款 256 像素 JPG 头像（经典线稿 28 款，其余四种风格各 20 款），资源位于 `miniprogram/assets/avatars/`，稳定编号、路径和内容哈希由 `miniprogram/builtin-avatars.js` 管理；原图文件名映射记录在 `docs/avatar-sources.json`。编辑资料选择后仅更新草稿，保存时通过现有资料接口发送 `avatar: "builtin:avatar-01"`。服务端校验编号白名单，读取随部署打包的图片并按既有内容哈希机制存储，继续返回 `/api/avatars/<hash>`，无需数据库迁移。资料页、排行榜及网页版沿用现有头像展示。Docker 镜像包含同一份目录和图片资源，部署须先更新服务端及网页版，再发布小程序；本次关闭上传无需数据库迁移，也不删除已有头像。
