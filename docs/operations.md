# 归档、备份与连接维护

## 数据保留

服务启动一分钟后进行首次检查，此后默认每小时检查一次；每种数据每次最多处理 100 条，在同一个事务内提交。自动清理要求最近 48 小时内存在成功校验的本机备份，否则记录 `maintenance-skipped` 并保留数据。

| 数据 | 默认处理规则 |
| --- | --- |
| 准备阶段牌桌 | 7 天无活动后标记待清理，再等待 3 天；期间成员打开牌桌或进行操作会取消待清理状态 |
| 已结束／已终止牌桌 | 30 天无活动后清理过程数据，先确保现有结算记录已归档；缺少结算快照的旧结束牌桌保留，供人工检查 |
| 正在进行的牌桌 | 不自动清理 |
| 房间列表失效条目 | 失效超过 90 天且没有备注时清理；带备注条目保留 |
| 登录会话 | 到期后分批清理，不影响有效会话 |
| 操作回执 | 超过 90 天后移除结果正文，永久保留账号与请求编号的去重标记 |
| 战绩、积分、趣味记录、对局管理状态、个人资料、管理审计 | 保留，不在自动清理范围内 |

“活动”指成员访问牌桌详情或更新牌桌。访问时间最多每小时写入一次；处于待清理状态的访问立即取消标记。仅浏览房间列表不会延长牌桌寿命。清理结束牌桌不删除独立归档，因此个人战绩与排行榜仍可查询。旧房间索引在升级启动时补齐，后续房间列表不再逐次扫描全部房间 JSON。

新客户端的请求编号包含生成时间：未被处理且超过 30 天、或比服务端时间快超过 5 分钟的请求返回 410；已有回执仍可查询，清理后的编号也返回 410，不会重新执行。旧客户端的编号继续兼容，去重标记长期保留以防回执清理后重复扣分或重复操作。设备时间异常时应先校准时钟。SQLite 删除后的页供后续写入复用，不会主动执行阻塞写入的 `VACUUM` 缩小文件。

### 配置

通过运行环境或 Compose 的 `app.env` 注入；Node 不自动读取 `.env`。

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `CLEANUP_ENABLED` | `1` | 设置 `0` 暂停自动清理，备份继续运行 |
| `CLEANUP_INTERVAL_MINUTES` | `60` | 检查间隔，1–1440 分钟 |
| `CLEANUP_BATCH_SIZE` | `100` | 每类数据每批上限，1–1000 条 |
| `ROOM_LOBBY_RETENTION_DAYS` | `7` | 准备牌桌无活动保留天数 |
| `ROOM_GRACE_DAYS` | `3` | 准备牌桌标记后的宽限天数 |
| `ROOM_ENDED_RETENTION_DAYS` | `30` | 结束／终止牌桌无活动保留天数 |
| `ROOM_ENTRY_RETENTION_DAYS` | `90` | 无备注的失效房间条目保留天数 |
| `RECEIPT_RETENTION_DAYS` | `90` | 操作结果正文保留天数 |
| `BACKUP_DIR` | 数据库同目录的 `backups/` | 本机备份位置；Compose 固定为 `/data/backups` |

天数必须为 1–3650 的整数；非法数值在启动时拒绝。大量历史数据会分批消化，不在启动时一次性删除。

## 本机在线备份

服务启动约一秒后检查备份，此后每小时检查；没有可用备份或上次备份距今已满 24 小时时生成新快照。SQLite 在线备份在独立工作线程执行，包含已提交到 WAL 的数据。完成完整性校验、关键表计数和文件同步后才发布正式文件，失败不会触发旧快照清理。

新建备份目录权限为 `0700`，文件为 `0600`。容器内 `/data/backups` 对应主机 `/opt/shadowtable/data/backups`。只清理由本功能生成的 `shadowtable-<UTC时间>.sqlite` 文件，保留最近 7 天每天、最近 28 天每周、当前及前两个月每月的最新快照，重复项合并，并始终保留最新一份。其他文件不受保留策略影响。

当前仅配置本机备份，没有对象存储、异机上传或外部凭据。本机磁盘整体损坏时仍需外部备份才能恢复；外部目标后续另行配置。本次应用改动不会管理主机上已有的其他备份定时器。

手工备份与校验（将路径替换为实际位置）：

```sh
npm run backup -- create data/shadowtable.sqlite data/backups
npm run backup -- verify data/backups/shadowtable-2026-10-02T00-00-00-000Z.sqlite
```

容器中可用 `bash /opt/shadowtable/current/compose.sh exec -T app node server/backup.js verify /data/backups/<文件名>.sqlite` 校验指定快照。校验执行完整 `PRAGMA integrity_check` 并返回关键表计数；它不修改在线数据库。手工 CLI 备份不会更新运行中服务的自动备份状态。

### 恢复与版本回退

1. 先校验指定快照，将其复制到独立的临时目录，使用当前版本检查登录会话、房间、个人战绩和积分；不得在同一个数据文件上同时启动两个写入服务。
2. 确定恢复时间点与可能损失的后续写入，进入维护窗口，停止唯一的应用写入进程。
3. 将当前主数据库及同名 `-wal`、`-shm` 一起保存在独立回退目录；把验证过的快照复制为原 `DB_PATH`，恢复应用用户所有权与文件权限。不能让旧 WAL/SHM 与恢复的主数据库混用，也不要直接把保留目录中的快照当在线数据库打开。
4. 启动当前兼容版本，检查 `/health`、房间恢复、个人记录和日志。确认恢复成功前保留原数据副本。

发布前的停写备份继续保留，包含主库及 WAL，但排除数据目录中的 `backups/`，避免重复打包日常快照。发布失败自动回退只恢复应用镜像，不回滚数据库。

首次发布可先设置 `CLEANUP_ENABLED=0`，确认备份和业务验收通过后启用。**回执正文已被清理后，不得直接回退到不识别 `receipt_tombstones` 的旧版本**：旧版本可能将历史请求当作新操作。关闭清理不能恢复已经删掉的正文，需选支持去重标记的版本或制定停写数据恢复方案。其他新增表／列采用增量迁移，但不代表所有历史版本都兼容清理后的数据。

## 连接稳定性

- 网页请求默认 10 秒超时；网络错误、5xx 与 429 自动进入恢复流程，显示重连状态。指数退避加入随机抖动，最高约 15 秒；429 遵守服务端 `Retry-After`，不会提前重试。切后台暂停轮询，回前台或恢复网络后及时重试。
- 未确认操作使用原请求编号和原内容核对，确认前保持重复提交保护；身份过期停止自动操作，要求重新登录。旧请求的迟到 401 不会清除新会话。
- 小程序沿用自动重连，并与网页统一公共牌桌 ETag。只缓存当前会话下的公共详情，私密身份和管理接口不进入该缓存；任何写操作使缓存失效。服务端先鉴权再判断 304，权限变化立即生效。
- 进行中牌桌保持 2.5 秒轮询；准备、结束、终止阶段连续无变化时逐步放慢至 10 秒。成功提交后立即同步。
- 登录请求合并，减少同一客户端同时刷新时的重复登录；读取额度与写入额度分离，轮询不会耗尽操作额度。

### 可信代理与观测

直接运行 Node 时，`TRUSTED_PROXY_CIDRS` 默认留空，不接受转发头作为限流地址。经过代理时只填实际网关 IP/CIDR，逗号分隔；按从右向左的可信代理链解析 `X-Forwarded-For`。非可信连接或非法头一律使用连接来源地址。

仓库的 `compose.sh` 自动读取专用 `shadowtable_proxy` 网络网段并注入可信范围；该网络只放网关与应用，应用端口不向公网开放。不要手工配置全网信任或把不可信容器接入该网络。经正确网关转发后，限流按玩家来源地址区分；同一公网 IP 仍共享登录 60 次／分钟、总请求 6000 次／分钟的额度。登录后账号读取 180 次／分钟、写入 60 次／分钟，资料修改和建房还有独立限制。

服务端每分钟输出有请求时的 `http-metrics`：请求数、状态码分布和 P95 延迟桶上界；不记录玩家身份、秘密内容或请求路径。`backup`、`backup-failed`、`maintenance`、`maintenance-failed` 和 `maintenance-skipped` 记录备份及清理结果。部署后留意备份失败、48 小时无备份导致清理暂停、持续 429/5xx 和延迟上升。
